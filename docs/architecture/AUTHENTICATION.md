# Authentication and account lifecycle

Filament 5 authenticates staff under `/admin`; there is no public self-registration. The panel uses its login throttling, session regeneration and logout flow. It rejects accounts whose status is not `active` or that lack `admin.access`. Login and logout events create safe audit entries, and successful login updates `last_login_at`.

Administrators create accounts through `UserManager`. It normalizes email, validates uniqueness, stores a random inaccessible initial password through Laravel hashing, and sends a password-reset invitation. The panel enables Filament's password reset flow, an audited staff profile page, and optional authenticator-app MFA with recovery codes. MFA secrets and recovery codes are encrypted at rest and hidden from serialization. Council security policy must decide when privileged MFA becomes mandatory before production. Configure a secure mail transport before creating accounts; the action rejects the log mailer to avoid writing reset links to application logs. A new account has no role until an authorized System Administrator assigns one. Users can be disabled or reactivated through audited actions. A disabled account cannot access Filament even if its session or roles remain. No public registration route exists.

For the first account, seed roles and permissions, then run `php artisan security:bootstrap-admin` in an interactive trusted terminal. The command refuses to run when an active System Administrator exists, requires a strong password, and records a bootstrap audit event. Do not pass a password on the command line. Deployment should run migrations before opening traffic after a Stage 1 upgrade.
